# Organizer Acceptance Test

Verifies that an organizer can run a complete Open Play session end-to-end:
Create Session → Register Players → Check-in → Generate Matchups → Score
Entry → Court Rotation → Waiting Queue → Manual Court Assignment → Player
Replacement → Session Settings → Standings → History → End Session.

This document has three parts:

1. **Automated coverage** — what's checked by `scripts/run-acceptance-test.mjs`, and its limits.
2. **Manual test scenarios** — a step-by-step checklist for a human to run against the live app.
3. **Findings** — workflow gaps and dead ends found while writing this, with severity. Nothing here has been fixed yet (see each finding's note).

## 1. Automated coverage

```
node scripts/run-acceptance-test.mjs
```

Drives a full organizer session through the same pure functions the app uses
(`src/lib/utils.js`, `src/lib/performanceRating.js`, `src/lib/constants.js`)
— create → register → check in → generate matchups → deploy/score/end a
match → manual court assignment → player replacement → session settings →
standings → history — asserting the data comes out shaped exactly like the
real app produces it.

**What it does NOT cover:** anything about the UI itself — clicking,
rendering, disabled/enabled button states, dialogs, toasts, navigation. It
is a data/logic regression test, not a UI test (see the plan discussion:
this project has no UI test framework installed, and adding one, e.g.
Playwright, was deliberately deferred rather than done silently). All 42
assertions currently pass. **Section 2 below is what actually covers the UI.**

### TV Mode - Live Courts Clipping Fix
Bug reported 2026-07-24: with 3-4 live courts (the 2x2 grid breakpoint in `courtGridDimensions`), the second team's player row was clipped and invisible. Root cause: `courtSizeTier` was keyed only on grid COLUMN count, so a 2x2 grid (2 columns, 2 rows — each card getting only half the column's height) still used the "2 columns, 1 row" tier's larger avatar/font sizing, sized for a card with the FULL column height. `courtCard`'s `overflow: hidden` then silently clipped whatever didn't fit. Fixed by having `CourtCard` bump to the next-smaller tier whenever `rows >= 2 && columns === 2` (the same tier already used for 5-6 courts' 3x2 grid, confirmed to fit).
- [x] **All 4 players visible on every live court.** Verified against the same live session (3 live courts, 2x2 grid) that originally showed the bug — direct DOM measurement (`scrollHeight` vs `clientHeight`) on every court card at 1920×1080 confirms zero overflow (previously ~176-180px of clipped content per card); confirmed visually via screenshot too.
- [x] **1-2 and 5+ court layouts unaffected.** The fix only changes sizing for the specific `columns === 2 && rows >= 2` case (3-4 live courts) — all other court counts use the exact tier they used before.
- [x] **No regression.** `node scripts/run-acceptance-test.mjs` re-run after this change — still 42/42 passed.

### Bug fix — Smart Court Dispatch didn't populate multiple open courts
Verified 2026-08-02. Reported symptom: with 3 automatic open courts and enough eligible players, only Court 1 ever got dispatched — Courts 2 and 3 stayed open forever, with no upcoming matchups left to give them.

**Root cause:** `maxUpcomingMatchups` (`lib/utils.js`) computed the queue-depth cap as `Math.max(0, occupiedCount - 1)` — the moment even ONE court became occupied (e.g. Court 1 dispatched from the first 4 players checking in), the cap collapsed toward 0 for every later save, regardless of how many OTHER courts were still sitting open. Since `refreshNextMatchups` never built more matchups than that cap allowed, Courts 2 and 3 could never receive one, no matter how many more players checked in afterward. `dispatchAvailableCourts` itself (`lib/courtDispatch.js`) was not the problem — its per-court loop was already structurally capable of filling every open court in one pass, given enough matchups to work with; it was just being starved.

- [x] **The cap never drops below the number of courts still open right now.** `maxUpcomingMatchups` changed from `Math.max(0, occupiedCount - 1)` to `Math.max(openCount, occupiedCount - 1)` — verified directly: 2 occupied + 2 still-open courts (4 total) now yields a cap of 2 (was 1), enough to cover both open courts. Every other previously-verified case is unchanged: before session start (fill everything), 3 occupied + 1 open (cap 2), 4 fully occupied (cap 3, the literal "Live Courts − 1" steady state), 1 fully-occupied court with 0 open (cap 0, no artificial floor), and manual courts excluded from both counts.
- [x] **`dispatchAvailableCourts` is now an explicit iterative loop**, not a single `.map()` pass — a `for` loop over every court, selecting and removing the next dispatchable matchup per open court, stopping only when no automatic court remains open or no eligible matchup exists. Behaviorally identical to the prior implementation once given enough matchups (verified: existing dispatch tests still pass unchanged), but the structure now makes "keep going until courts or matchups run out" explicit and directly matches the requested architecture.
- [x] **Regression test reproduces the exact reported scenario end to end.** New `scripts/verify-court-dispatch.mjs` section 11 drives the real `maxUpcomingMatchups` + `refreshNextMatchups` (`lib/utils.js`) + `dispatchAvailableCourts` (`lib/courtDispatch.js`) together — the actual `save()` pipeline, not a simplified stand-in — simulating players trickling in across two separate save() calls (4 players, then 8 more) against 3 open automatic courts: the first save dispatches only Court 1 (correctly — only 4 players so far), the second dispatches both Court 2 and Court 3, leaving all 3 courts filled and zero players/matchups stranded.
- [x] **Held matches keep their priority; locked/held matches remain untouched; queue ordering preserved.** Unchanged — `selectNextDispatchableMatchup`'s selection logic was not touched, and `regenerateNextMatchups`'s locked/held protection was not touched.
- [x] **Works for every rotation mode; no matchmaking engine modified.** The fix lives entirely in `lib/utils.js` (the cap formula) and `lib/courtDispatch.js` (the dispatch loop's structure) — zero engine files touched. Verified live in the browser with a 3-court Continuous-queue session: 12 players checked in across two batches (4, then 8 more) reproduced the exact bug scenario and confirmed all 3 courts ended up `LIVE` with correct dispatch + voice-announcement Queue Activity Log entries for each.
