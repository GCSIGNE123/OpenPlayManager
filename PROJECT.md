# PROJECT.md

Reference doc for how this repository is organized and how the app works under the hood. For "how do I run this," see [README.md](README.md). For "how do I contribute a change," see [CONTRIBUTING.md](CONTRIBUTING.md).

## What this is

Open Play Manager is a web app for running pickleball open-play sessions: check-in with player photos, automatic doubles matchmaking, live scoring by court, standings, and a paid access-code gate for creating new sessions. It started as a Claude.ai artifact prototype and now lives here as a standalone Vite + React project backed by Supabase.

## Architecture

- **Screens and logic are split apart.** `src/PickleballOpenPlay.jsx` owns the top-level state (current screen, session data, auth) and the functions that mutate it (matchmaking, scoring, standings). Each screen (landing, organizer panel, session setup, live board, check-in, scorer, standings) is its own component under `src/components/`, receiving state and callbacks as props.
- **CONNECT.PH theme, centralized in one `:root` block.** `src/styles.js`'s `fontImport` string (injected once via a `<style>` tag) defines every color the app uses as a CSS custom property, extracted from the CONNECT.PH logo — Navy `--color-primary`, Orange `--color-secondary`, plus `--color-accent`/`-success`/`-warning`/`-error`/`-bg`/`-surface`/`-border`/`-text`/`-text-muted`/`-text-faint`/`-on-primary`. Nothing in the app hardcodes a hex color outside this one block — every style object references a `var(--color-...)`, so retheming means editing these ~15 lines, not hunting through components. The pre-existing `--ink`/`--court`/`--court-dark`/`--chalk`/`--ball`/`--coral`/`--line` names (which the hundreds of style objects throughout this file already reference) are kept as **aliases** onto the new palette (e.g. `--court: var(--color-primary)`) rather than renamed everywhere, so the whole app picked up the rebrand without every style object needing a rewrite. Two things worth knowing: (1) the vibrant brand orange is only ~2.4:1 contrast against a light background — well under WCAG AA's 4.5:1 for text — so `--color-secondary-text` (a darkened ~4.8:1 variant) exists specifically for when orange needs to *be* the text/foreground color on a light surface (see `styles.kicker` vs `styles.kickerOnDark`, used on the light Landing/Access screens vs. the navy session header respectively); (2) Progressive Skill Rotation's phase colors (`--color-phase-mentorship/-transition/-competitive` + `-tint` variants) and the rotating avatar palette (`--color-avatar-1..6`, used by `lib/utils.js`'s `colorForName`) are also defined here rather than as separate hardcoded arrays, for the same "one place to edit" reason.
- **Persistence is abstracted behind `src/storage.js`.** The app calls `window.storage.get/set/delete/list(key, shared)` — a shim with the same signature as the key/value API that Claude.ai artifacts get for free from their host environment. It's backed by a single Postgres table (`opl_kv`) in Supabase; see `supabase/schema.sql` for the schema and `backend/README.md` for setup.
- **Real-time sync via Supabase Realtime.** `storage.js` also exposes `subscribeToKey(key, shared, onChange)`, which opens a Postgres change-stream subscription. `PickleballOpenPlay.jsx` uses this instead of polling — any device's write shows up on every other connected device within about a second.
- **`DEV_ACCESS_CODE` — a permanent, never-expiring access code for the developer's own testing.** `lib/constants.js` hardcodes `"GUILSIGN"`; `submitAccessCode` in `PickleballOpenPlay.jsx` special-cases it before ever touching Supabase — no lookup, no `usedAt` check, always accepted straight to the Create Session screen — and `startSession` skips the normal "mark this access code used" bookkeeping when it's the code that validated. Every real organizer-issued code (`generateAccessCode`/`AdminPanel`) is still single-use exactly as before; this is the one exception, and it never creates or touches an `opl-access-*` Supabase record at all.
- **Auth is PIN-based, not account-based.** Scorer and Organizer/admin roles are gated by hardcoded PINs in `src/lib/constants.js` (`SCORER_PIN`, `ADMIN_PIN`), checked entirely client-side. Supabase row-level security does not enforce these — see `backend/README.md` for the trust model and what a real fix looks like.
- **Matchmaking is a pluggable Strategy (Strategy pattern), not hardcoded logic.** `src/engines/RotationEngine.js` defines the interface (`generateMatchups({ waitingIds, players, existingMatchups })` → new matchup objects); `src/engines/BalancedRotationEngine.js` is the main concrete implementation (always teams a beginner with an intermediate, avoids repeat partners/opponents by recency, greedy with randomized-restart tie-breaking — see the file's doc comments for the full priority order). `src/lib/utils.js`'s `getRotationEngine(rotationMode)` maps `state.rotationMode` to an engine instance, and `refreshNextMatchups`/`regenerateNextMatchups` are the only things that call it; swapping in a different mode later (King of the Court, DUPR Rotation, ...) means adding a new `RotationEngine` subclass and a case in `getRotationEngine`, not touching the app around it.
- **Matchups are built continuously, not in synchronized rounds.** Courts run independently and pick up a new match whenever they're free — there's no "everyone finishes round 3, then round 4 starts" lockstep. `refreshNextMatchups` runs after every state change and is deliberately *strict*: it only forms a matchup from a genuine 2-beginner + 2-intermediate group, never a same-skill fallback, because players check in one at a time and an eager fallback would permanently lock two beginners together moments before an intermediate arrives (matchups are immutable once built — only `reassignMatchup`/`substituteInMatchup`/the scorer's manual edits touch them). The same-skill fallback (last resort when the beginner/intermediate counts are genuinely unequal) is opt-in, and only runs from the explicit "Regenerate matchups" control in Scorer.
- **Per-player rotation history feeds the scoring.** Each player record tracks `partnerCounts`/`recentPartnerIds`, `opponentCounts`/`lastOpponentIds`/`recentOpponentIds`, and `courtCounts`/`lastCourt`, updated by `recordRotationHistory` when a match ends (see `PickleballOpenPlay.jsx`'s `endMatch`). `state.matchHistory` logs one record per completed match.
- **Session Settings dialog — edit session properties after the session starts.** A gear icon on Scorer's Session Information card opens `SessionSettingsDialog.jsx` (new: an actual modal overlay, `styles.dialogOverlay`/`dialogCard` — the first of its kind in this app, previously everything was inline panels). Editable: venue name (validated non-empty), expected games per player, and — only when Progressive Skill Rotation is the active mode — its two phase-boundary percentages. All edits are local draft state until "Save", which calls a single new `updateSessionSettings(updates)` in `PickleballOpenPlay.jsx` (`save({ ...state, ...updates })`, one write) so Cancel/closing the dialog discards everything cleanly. **Rotation Mode is deliberately excluded** — shown read-only inside the dialog for reference — preserving the earlier decision that it's chosen once at Create Session and can't drift mid-session (see above). Court count is also left out, since Scorer's existing +/- stepper already owns that.
- **Expected Games per Player, captured at Create Session.** `CreateSessionScreen.jsx` has a numeric field (step 4, default 6, clamped to ≥1) that's passed through `startSession` into `initial.expectedGamesPerPlayer` when the session is first written to Supabase. This is the same `state.expectedGamesPerPlayer` field Progressive Skill Rotation's phase calc (`calculateSessionProgress`/`progressiveSkillPhaseFor`) already reads and that `ProgressiveSkillPanel` already lets an organizer edit mid-session (Scorer, Settings panel) — Create Session just seeds its starting value regardless of which rotation mode is chosen, rather than everyone starting from the hardcoded default of 6. No other behavior currently reads it outside that existing Progressive Skill Rotation usage.
- **Session Type Architecture — Open Play vs. Tournament (architecture only, no tournament logic yet).** `state.sessionType` (`"openPlay"` | `"tournament"`, see `SESSION_TYPES` in `lib/constants.js`) is chosen on `CreateSessionScreen.jsx` (step 3: 1 Session name, 2 Number of courts, 3 Session type, 4 Rotation Strategy *or* Tournament Format, 5 Expected games per player — Open Play only, 6 Register players) via a two-button toggle, same pattern as `SkillToggle`. It gates step 4 and step 5: **Open Play** → the existing Rotation Strategy `<select>` (`ROTATION_MODES`, unchanged logic) *and* the Expected Games per Player field; **Tournament** → both of those are hidden, replaced by a Tournament Format `<select>` (`state.tournamentFormat`, see `TOURNAMENT_FORMATS` — Round Robin / Single Elimination / Double Elimination — the last two explicitly marked as placeholders in the UI copy). Selecting a Tournament session does not currently change any runtime behavior — Scorer, the rotation engines, and everything else still key off `rotationMode` alone, which continues to default to `"continuous"` regardless of `sessionType`; a Tournament session today is functionally identical to an Open Play one.
  - **Naming decision, worth knowing:** the stored/internal field is still `rotationMode`, not `rotationStrategy` — "Rotation Strategy" is the UI label and conceptual grouping only. Every rotation engine (`getRotationEngine`, `refreshNextMatchups`/`regenerateNextMatchups`, `isPoolingRotation`, `progressiveSkillPhaseFor`), `ScorerView.jsx`, `PickleballOpenPlay.jsx`, and `RotationSimulationEngine.js` all still read/write `rotationMode` untouched. A literal field rename was considered and deliberately rejected: it would touch every one of those call sites for a purely cosmetic change, and — more importantly — old Supabase session records only have `rotationMode`, so a rename would either need a compatibility shim or silently lose old sessions' rotation setting on load. `sessionType` and `tournamentFormat` are genuinely new fields (old records simply lack them, which is harmless since nothing yet reads `sessionType` downstream of Create Session) — `rotationMode` is not.
- **Player Database — a reusable, cross-session player registry (architecture only; no statistics/rankings/tournament logic yet).** `src/lib/playerDatabase.js` stores one Supabase KV record per player (`opl-player-{id}`, shared, listed by prefix — `PLAYER_DB_PREFIX` in `lib/constants.js`), the same one-record-per-entity pattern sessions and access codes already use, deliberately not a single aggregate blob (which would need a full read-modify-write on every add and risks two organizers clobbering each other). A record: `id, firstName, lastName (nullable), displayName, photo, gender (nullable), skill, duprRating (nullable), contactNumber (nullable), notes (nullable), active, createdAt, updatedAt`.
  - **The identity link that makes this a real "single source of truth":** a *session's* per-player record (`state.players[id]` in `PickleballOpenPlay.jsx` — games/wins/losses/checkedIn/skipped, reset fresh every session) is completely unchanged in shape and stays that way. What changed is where its `id` comes from: `CreateSessionScreen.jsx` now reuses the Player Database record's own id as the roster entry's id, whether that player was picked from the database or just created. That means a future Statistics/Rankings/Season-History feature can join a player's results across every session they've ever played purely by id — no migration, no name-matching heuristics, because the id has been consistent since the record was first created.
  - **Create Session's registration step (step 6)** now offers **Select existing player** (a search box, active players only, styled like the existing `PlayerPicker` search pattern — already-added players show "Added" and can't be re-added) and **Create new player** (First Name required, Last Name/Display Name/Skill/Photo as the primary fields, with Gender/DUPR rating/Contact number/Notes tucked into a collapsible "More details" section so the fast path stays fast). Creating a player always saves it to the database *and* adds it to the current roster in one action — this is also what satisfies "auto-create records if no database exists yet": there's no seed/migration script, the database simply starts empty and grows from the first player anyone creates. A save failure doesn't block the organizer — the player still joins the local roster, with a warning surfaced — since a background persistence failure shouldn't stop someone from starting their session.
  - **Deliberately out of scope:** Check-in's walk-in add (`quickAddCheckIn` in `PickleballOpenPlay.jsx`) is untouched — walk-ins remain session-only, not saved to the database. There's also no player-management screen yet (editing an existing record, or setting `active: false`) — `active` defaults to `true` and nothing currently changes it. Both are natural follow-up tasks, not done here to keep this one architectural change scoped.
- **Tournament Engine Foundation — the shared architecture every tournament format plugs into (architecture only; no elimination/standings/seeding/champion logic yet).** Built on top of the Round Robin Scheduler below, extending its data model and formalizing a Strategy-pattern interface for format engines to share, the same role `RotationEngine` plays for Open Play's rotation strategies:
  - **Extended data model** (`src/lib/tournamentModel.js`, additive fields — old stored tournament records simply lack them, harmless since nothing reads them yet): `Tournament` gains `name` and `status` (`draft`|`ready`|`running`|`completed` — a freshly generated tournament starts `"ready"` since it already has its full schedule; nothing transitions it further yet, no live match tracking exists). `TournamentRound` gains `status` (mirrors match status) and `courtAssignments` (the round's court numbers, redundant with but surfaced alongside `matches[].court`). `TournamentMatch` gains `winner` and `score`, both `null` until match scoring is actually built. The former "entrant" is now formally the **Tournament Participant** model — `makeParticipant(label, playerIds, seed)` → `{ id, label, playerIds, seed, status }`; `makeEntrant` (the name the working scheduler already imports) is kept as an alias so nothing existing needed to change.
  - **`src/engines/TournamentEngine.js`** — the abstract base class: `generateSchedule()`, `updateMatchResult()`, `getStandings()`, `getNextMatches()`, each throwing by default, exactly mirroring `RotationEngine`'s own single-method version of this pattern. `RoundRobinEngine`/`SingleEliminationEngine`/`DoubleEliminationEngine` (all three in `src/engines/`) extend it.
  - **`RoundRobinEngine.generateSchedule()` is real** — it delegates straight to the already-working `RoundRobinScheduler` (see below), so building this foundation didn't regress the shipped feature; that's the *only* real method across all three engines. Every other method on all three (`updateMatchResult`/`getStandings`/`getNextMatches`, plus all four methods on Single/Double Elimination) returns an inert `{ implemented: false, message }` placeholder rather than throwing, so a future caller exploring the interface doesn't crash on formats/methods that aren't built yet.
  - **`getTournamentEngine(format)`** (`src/lib/tournament.js`) — a format → engine instance registry, additive and not wired into the existing `buildAndSaveRoundRobinTournament` call path (which still calls `RoundRobinScheduler` directly, deliberately untouched so the shipped flow can't regress). It exists for a future caller — e.g. a Dashboard action — that wants to go through the generic interface instead.
  - **Tournament Dashboard UI**: the session nav's tournament-only tab is now labeled **"Tournament"** (was "Schedule") and renders `TournamentDashboardView.jsx` — five sub-tabs: Overview, Participants, Schedule, Standings, Bracket. Only **Schedule** is real (it's `TournamentScheduleView.jsx`, unchanged, nested unmodified inside the new Dashboard); Overview/Participants/Standings/Bracket are static "Coming soon" placeholder panels with no data or logic, per this task's explicit scope.
- **Round Robin Scheduler — Tournament Manager's first format (schedule generation + display only; no scoring/standings/brackets yet).** Three independent pieces, deliberately not reusing Open Play's `courts`/`nextMatchups`/`matchHistory` shapes:
  - **Data model** (`src/lib/tournamentModel.js`): `Tournament` → `TournamentRound` → `TournamentMatch` (field lists now extended — see Tournament Engine Foundation above). Stored the same way as the Player Database — one KV record per tournament (`opl-tournament-{id}`, `TOURNAMENT_PREFIX`), never embedded in the session's own state blob. A session only carries a `tournamentId` pointer (`state.tournamentId`, additive/nullable — old sessions simply don't have one).
  - **Engine** (`src/engines/RoundRobinScheduler.js`): the classic circle/polygon method — fix one entrant, rotate every other entrant one seat per round — which guarantees every pair meets exactly once in the minimum number of rounds, with no search/backtracking needed. Deliberately does **not** extend `RotationEngine` (or, now, `TournamentEngine` — it predates that base class and is wrapped by `RoundRobinEngine` instead, see above): that interface is "generate the next matchup from a live, continuously-changing queue" (Open Play); this is "generate the entire schedule up front from a fixed, known entrant list" — a different problem. An "entrant"/Participant is generic (single player for Singles, pre-formed 2-player team for Doubles), so the engine itself never needs to know which mode produced it. Odd entrant count → a synthetic BYE entrant is added so the circle method's even-count requirement is met; the circle method's own symmetry then guarantees every real entrant draws exactly one bye, recorded as a real (visible, `isBye: true`) match rather than silently dropped. Court numbers are assigned by cycling `1..courtsCount` within each round — there's no "wait for a free court" sequencing logic, since this task only generates a schedule, not a live running order. A separate `pairIntoTeams` helper handles Doubles' player→team step (simple sequential pairing, not seeded — "Seeding" is already its own later `FEATURES.md` item); it throws rather than silently benching someone if the player count is odd, since deciding who sits out the whole tournament isn't this function's call to make.
  - **Orchestration** (`src/lib/tournament.js`): the only piece that knows about session players — builds entrants from `state.players` (via `pairIntoTeams` for Doubles), calls the engine, and persists the result.
  - **UI**: `TournamentScheduleView.jsx` (now nested inside the Tournament Dashboard's Schedule sub-tab — see above) always shows the Singles/Doubles toggle and a Generate/Regenerate button (kept visible even after a schedule exists, so switching modes doesn't require a dead end); regenerating creates a brand-new Tournament record with a new id rather than overwriting the old one in place, since nothing references match ids yet, so a failed regenerate (e.g. odd player count for Doubles) can surface an error without corrupting the currently-displayed schedule. Rounds render as expandable cards (reusing `HistoryView`'s round-card styles) showing Court, both teams, and a static `Pending`/`In Progress`/`Completed` status badge — the badge never transitions; nothing writes to `status`.
  - **Explicitly not built:** standings, match scoring, rankings, champion calculation, knockout brackets — all separate future `FEATURES.md` items.
- **Three rotation modes, chosen once at Create Session.** `state.rotationMode` ("continuous" | "winnerPool" | "progressiveSkill", default `"continuous"`) is selected on `CreateSessionScreen.jsx` (step 3, alongside venue name/court count) and baked into `initial.rotationMode` when `startSession` writes the session's first Supabase record — there's no later control to switch it, so it can't drift mid-session. Scorer shows the active mode inside a read-only **Session Information card** at the top of the page (`ScorerView.jsx` — Rotation Mode, Courts, Players, Waiting Players, Current Round; Rotation Mode is looked up from `ROTATION_MODES`, no setter passed down) rather than a dropdown, since the underlying rotation logic (`getRotationEngine`, `refreshNextMatchups`/`regenerateNextMatchups`, `isPoolingRotation`) is untouched by where the mode gets picked. "Current Round" is `matchHistory.length + 1` — the same round number `endMatch` would assign to the next completed match, so it always matches what Game History will show once that match ends. It still decides between:
  - **Continuous queue** (default) — the model described above: every court draws independently from one shared waiting queue.
  - **Winner Pool Rotation** — courts pair up by fixed adjacent position (court 1 & 2, 3 & 4, ...). When *both* courts in a pair have finished, `src/lib/winnerPoolRound.js`'s `resolveWinnerPoolMatch` pools their 4 winners into one new match (via `WinnerPoolRotationEngine`, always 1 beginner + 1 intermediate per team, avoiding the immediately-previous partner and opponent) and their 4 losers into another. Both courts in the pair open up (not redeployed to directly) and the two new matchups join the *back* of `nextMatchups` — so anyone else who's been waiting gets first claim on the now-open courts via the normal "Assign match"/"Fill all open courts" flow, and the just-finished 8 players don't just keep replaying each other while everyone else sits out. A court that finishes before its partner shows a distinct "WAITING" state (`court.awaitingPair`) with the final score locked in, rather than being emptied — see `CourtCard.jsx`. This is the one deliberate, explicitly-scoped exception to "continuous, not lockstep" above: it's a hard requirement of the mode itself (pooling needs both courts' results at once), not incidental round-based phrasing, and it's pairwise (only the 2 courts in a pool wait on each other) rather than a full-session lockstep. The odd court out, when the courts array has an odd length, falls back to the continuous model's normal per-court requeue.
  - **Progressive Skill Rotation** — selectable end-to-end (picker, engine wiring, matchup generation, standard continuous-queue court lifecycle *outside Mentorship — see below*) and now phase-aware. `state.expectedGamesPerPlayer` (organizer-configurable in Scorer, default 6) and `src/lib/progressiveSkillPhase.js`'s `calculateSessionProgress`/`getProgressivePhase` compute the average games-played-so-far across checked-in players as a percentage of that target, and classify it into one of three phases — Mentorship, Transition, Competitive, with organizer-configurable boundaries (`state.progressiveSkillThresholds`, default 0–30% / 31–60% / 61–100%; `buildPhases` clamps/orders any input into a valid, non-zero-width set of zones). The active phase is threaded through `refreshNextMatchups`/`regenerateNextMatchups` (as `phase`, computed by `progressiveSkillPhaseFor` — lives in `lib/progressiveSkillPhase.js` itself so headless callers like `RotationSimulationEngine` can compute it too, without importing a React component) into `ProgressiveSkillRotationStrategy.generateMatchups({ ..., phase })`:
    - **Mentorship** — pairing delegates straight to `BalancedRotationEngine` (composed, not duplicated): prioritize beginner+intermediate teams, avoid repeating a player's most recent partner, minimize repeated opponents — the same scoring Continuous queue mode uses. Court *lifecycle* also switches to Winner Pool Rotation's pairwise pooling mechanic while this phase is active (`isPoolingRotation` in `lib/winnerPoolRound.js` gates on `rotationMode === "winnerPool"` OR `rotationMode === "progressiveSkill" && phase === "mentorship"`): courts pair up 1&2/3&4/..., a court that finishes first holds ("WAITING") until its pair partner also finishes, then both courts' winners pool into one new match and both courts' losers into another (via the same `WinnerPoolRotationEngine`/`resolveWinnerPoolMatch` standalone Winner Pool Rotation uses), joining the *back* of `nextMatchups` rather than redeploying straight onto the same two courts. If the session's phase crosses out of Mentorship while a court is already held "awaitingPair", `endMatch` still resolves that pooling when its partner finishes (checked independently of the *current* phase) so a phase boundary crossed mid-pair can't strand a court in the held state forever.
    - **Transition** — delegates to `TransitionRotationEngine`. Team formation: avoid a player's most recently repeated partner (same recency scale as Mentorship), plus a soft +30 bonus for a beginner+intermediate pairing — a preference, not a requirement, so a same-skill team is never blocked when it's genuinely the best available option (e.g. every mixed pairing would repeat a recent partner). Matchup formation: avoid repeated opponents (same recency scale), then use Performance Rating (`lib/performanceRating.js`) as a match-quality factor — the two teams' composite rating (average of their players' ratings, with not-yet-rated players treated as a neutral 50) is compared, and a bigger gap is penalized, so a hot team is less likely to be paired against a cold one. Same randomized-restart hedge (`bestOfAttempts`) as `BalancedRotationEngine` against greedy tie-breaking.
    - **Competitive** — delegates to `CompetitiveRotationEngine`. Ignores the original beginner/intermediate labels entirely — no bonus, no requirement. Team formation is primarily by Performance Rating closeness (players end up tiered with others at a similar level right now, weighted ~2x a full partner-recency swing so it dominates), with partner-recency avoidance still able to outweigh a small rating gap when a genuine repeat-partner conflict exists. Matchup formation avoids repeated opponents (same recency scoring as every other engine here); no separate rating-balancing pass, since teams are already rating-tiered from the partner stage. Same randomized-restart hedge (`bestOfAttempts`) as the other engines.
  - **Progressive Skill Rotation's UI** lives in `src/components/ProgressiveSkillPanel.jsx`, rendered in Scorer only when this mode is active: an animated phase badge (CSS `@keyframes phasePop`, restarted on every phase change via `key={activePhase.key}` forcing a remount), a 3-zone progress bar (`buildPhases`-driven zone widths, a pulsing marker at the current session-progress position, `transition: left 0.5s ease` so it glides rather than jumps), a collapsible Settings panel (expected games/player, and the two phase-boundary percentages — reuses the same `expectedGamesPerPlayer` input from before, now alongside the new threshold inputs), and a per-phase match-count stats row. Match counts come from `matchHistory` entries tagged with the phase they were actually played under (`endMatch` computes this from the *pre-match* state, since games-played only increments after a match ends) — so the stats reflect the session's real history, not just whatever phase happens to be active right now.
- **Session-only Performance Rating.** `src/lib/performanceRating.js`'s `calculatePerformanceRating(player)` derives a single 0-100 number from stats already tracked per player — wins, losses, games played, current streak, and point differential (`pointsFor - pointsAgainst`) — weighted so win rate dominates, with average point differential and streak as smaller adjustments; `null` until a player's first completed game. It's not a real skill rating (like DUPR), just an at-a-glance "who's playing well today" indicator. Shown as a colored badge next to each player in Standings (with a new RTG column) and in Scorer's waiting players list. Session-only by construction — every input stat already resets to 0 when a session is created (see the `players` object built in `createSession`) and nothing persists beyond that session's own storage key, so no separate reset logic was needed.
- **Standings: sortable columns, computed client-side.** `StandingsView.jsx` derives `gp` (`wins + losses`) alongside the existing `diff`/`performance` per-row fields — no new state field, always in sync with `matchHistory` since it's recomputed from `players` on every render. Clicking a sortable column header (`GP`/`W`/`L`/`+/-`/`RTG`) cycles `null → "asc" → "desc" → null` for that column via two `useState`s (`sortKey`, `sortDir`); only one column can be active since they share the same state pair. With no active sort, rows fall back to the default order — highest Rating, then highest Wins, then highest point differential, then alphabetical name (`defaultCompare`) — matching (and formalizing) the ranking the page always used. Sorting is a plain in-memory `.sort()` over already-loaded `players`, so it's instant and needs no round-trip; `SORT_COLUMNS` (an array of `{ key, label, getValue }`) is the single place a sortable column is defined, driving both the header buttons and the comparator.
- **Organizer controls in Scorer.** Manual swap: `reassignTeams`/`substitutePlayer` edit a *live* court's teams; `reassignMatchup`/`substituteInMatchup` edit an upcoming (not-yet-deployed) matchup — both draw only from players not already locked into something else, so the two features can't fight over the same player. Lock: `toggleLockMatchup` protects one matchup from `regenerateMatchups` (a full "rebuild everything not-locked" rerun of the active rotation engine over the current waiting pool) while everything else about it (Fix teams/Substitute) stays editable. Preview before publishing: `nextMatchups` is a pre-built, scorer-reviewable list — "Assign match"/"Fill all open courts" is the only thing that deploys a matchup from that list onto an actual court, so nothing goes live without appearing in Scorer first. Undo: two one-shot, device-local snapshots (not synced to Supabase, so they're a quick "oops" for whoever just clicked, not a durable multi-device feature) — `regenerateSnapshot` (`undoRegenerate`, restores `nextMatchups` to before the last Regenerate) and `lastRoundSnapshot` (`undoLastRound`, restores the *entire* pre-match state — court back to live with its original teams/score, players' stats and rotation history reverted, `matchHistory` entry removed, `queueIds` back to not having those players requeued — from right before the last "End match"). Both are cleared by `clearOneShotSnapshots()` at every point that could make restoring them unsafe (deploying a matchup, editing a matchup, another regenerate/end-match, skipping/removing a player, a new check-in, leaving the session) so neither can ever silently resurrect a player or round that's since moved on.
- **Replacement sourcing: Waiting Queue + Upcoming Matchups, and "Move to Queue".** Real Open Play sessions often need to pull a replacement from someone already scheduled into a later matchup, not just the waiting queue. `lib/utils.js`'s `buildReplacementCandidates(nextMatchups, unassignedPlayers, players, excludeMatchupId)` returns `{ waiting, upcoming }` — `upcoming` entries are tagged with `scheduledLabel` (the same "Next up" / "Then · matchup N" text Scorer already shows above each matchup card, so a candidate's tag always matches what's on screen) and `matchupId`; `excludeMatchupId` leaves out the matchup currently being edited so a substitution never offers one of its own teammates/opponents as its own replacement. `PlayerPicker` renders both pools as separate labeled sections. Picking a candidate from `upcoming` runs `dissolveMatchupIfReserved(nextMatchups, playerId, exceptMatchupId)` first — a matchup can't exist with only 3 players, so pulling one out always tears the *whole* matchup down, freeing all 4 back to the unassigned pool (they never left `queueIds` — see `reservedMatchupIds` — so nothing needs re-adding). The next `refreshNextMatchups` (every `save()` runs one) automatically rebuilds fresh matchups from that larger pool via the session's *active* rotation engine, so Progressive Skill Rotation's pairing logic decides who plays whom next — this doesn't bypass or duplicate that algorithm, and never touches `matchHistory`, `players` stats, or anything about a completed match. Both `substitutePlayer` (live court) and `substituteInMatchup` (upcoming matchup) call `dissolveMatchupIfReserved` on their incoming player before making the swap, so either flow works identically whether the replacement came from the queue or another matchup. **"Move to Queue"** (`moveToQueue(playerId)`, a "↩" button on every `PlayerChip` inside an upcoming matchup — i.e. every player who hasn't started their next scheduled game) is the same `dissolveMatchupIfReserved` call on its own: an organizer-initiated way to pull someone out and make them immediately available, without pairing it with an immediate substitution elsewhere.
- **Manual Court Assignment.** Each court has `assignmentMode` (`"automatic"` | `"manual"`, toggle only shown while `status === "open"`) and `manualLocked`, added to `emptyCourt` in `lib/constants.js`. Switching a court to Manual clears its `teamA`/`teamB` and lets the organizer build a draft directly in those same arrays — filling a slot (`setManualCourtPlayer`, sourced from the same `PlayerPicker`/`buildReplacementCandidates` waiting-queue + upcoming-matchups pools the replacement-sourcing feature uses, including `dissolveMatchupIfReserved` for a pick coming out of an upcoming matchup) requires no data transformation once locked, since a manual court's draft already has the exact shape a live court needs. `lib/utils.js`'s `manuallyReservedIds(courts)` is the single source of truth for "this player is spoken for by a manual court" — `save()` filters it out of the pool passed to `refreshNextMatchups` on *every* state change (not just an explicit action), so the automatic rotation engine permanently ignores anyone drafted or locked into a manual court, matching "should integrate seamlessly ... and only affect future match generation." `lockManualCourt` validates exactly 2 unique players per side (4 unique total) before flipping `status` to `"live"`/`manualLocked: true` — from there it behaves exactly like any other live court (same score/end-match/Fix teams flow; `matchHistory` and player stats are untouched by any of this). `unlockManualCourt` (available on a live, still-unfinished manually-locked court) reverses the lock, returning its 4 players to `queueIds` and clearing the draft back to an empty Manual court — a match reaching `"finished"`/`endMatch` releases the lock on its own via the normal flow instead. `generateRemainingCourts` ("Generate Remaining Courts" button) is the one-click version of the organizer workflow's last step: rebuilds `nextMatchups` from scratch (`regenerateNextMatchups`, same call "Regenerate matchups" uses) over a pool pre-filtered by `manuallyReservedIds`, then deploys the results onto every open *automatic* court, leaving manual courts (draft or locked) completely alone. UI: the Automatic/Manual toggle and slot editor live in `CourtCard.jsx` (shown only pre-lock), with a "🔒 Manual Assignment" badge replacing the normal status tag once locked, and an "Unlock" button alongside "Fix teams" while live.
- **Game History — read-only, grouped by round.** `src/components/HistoryView.jsx` (a new "History" nav tab, alongside Live Board/Check In/Standings/Scorer) renders `state.matchHistory` — already-stored, already-immutable completed-match records — with zero writes back to state, so it can never itself change what actually happened. Grouped into expandable round cards (`matchRecord.round`, which — consistent with this app's continuous, non-lockstep architecture, see "Matchups are built continuously" above — is the order matches actually *finished* in, not a synchronized "everyone plays round N together" batch; most sessions show one game per round card, reflecting that courts run independently); the most-recently-completed round starts expanded, every earlier one collapsed, with a click to toggle any round. Each match card shows court, both teams (score, winner highlighted), and completion time; clicking any player name opens a `PlayerHistoryPanel` — every game that player's been in, their partner/opponents/result per round, and a games/W-L/courts-played summary, computed by filtering `matchHistory` for that player id, nothing pre-aggregated or cached. A combined search box (matches player name, round number, or court number) plus separate round/court dropdown filters narrow the round cards shown. "Match Duration" isn't tracked — the app doesn't currently record a match's start time anywhere, only `endedAt` — so it's omitted rather than faked; would need a `startedAt` added at deploy-time (`fillCourt`/`lockManualCourt`/etc.) if a future task wants it. CSV/JSON export (`exportHistoryCsv`/`exportHistoryJson`) resolve player ids to names at export time only, client-side `Blob` + anchor-download, no server round-trip — `matchHistory` itself keeps storing ids, so a later name edit can't retroactively rewrite exported history. Future-compatibility note: `matchHistory` entries were already shaped for reuse (round/court/team ids/scores/winner/timestamp/phase) before this feature existed — History adds a read surface over that existing shape rather than a new one, so it stays reusable for player profiles/season stats/rankings/reports later.
- **Quick "Won" scoring.** `declareWinner(courtIdx, team)` skips point-by-point scoring for casual games — it sets the declared winner's score straight to 11 and the other team's to 0 and marks the court "finished", exactly as if `adjustScore` had been clicked eleven times. A "Won" button (`TeamRow`'s `onDeclareWinner`) sits next to each team; it's a shortcut into the existing score/status/`endMatch` flow, not a separate code path, so wins recorded this way behave identically everywhere (stats, `matchHistory`, rotation history) to a normally-scored 11-0 game.
- **Rotation simulation — headless engine, two front ends (CLI + a Developer page).** `src/lib/simulation/RotationSimulationEngine.js`'s `runSimulation(config)` plays out a complete Open Play session under Progressive Skill Rotation entirely in memory (browser or Node — it's plain JS, no server round-trip) and returns a structured result (`playerSummaries`, `matchLog`, `roundLog`, `phaseCounts`, `stopReason`, `fairnessStats`, etc.). It genuinely reuses the live app's matchmaking — `getRotationEngine`/`refreshNextMatchups` (which dispatch through `ProgressiveSkillRotationStrategy` to `BalancedRotationEngine`/`TransitionRotationEngine`/`CompetitiveRotationEngine` per phase), `progressiveSkillPhaseFor`, and the Winner Pool Rotation pooling mechanic (`isPoolingRotation`/`resolveWinnerPoolMatch`) that Mentorship phase borrows — none of that is reimplemented. What the engine *does* supply itself is the round-by-round orchestration a live UI drives one click at a time (`fillAllOpenCourts`, `endMatchAt`, mirroring `PickleballOpenPlay.jsx`'s `fillAllCourts`/`endMatch` field-for-field) — those aren't pure functions in the app today, since they're React state setters, so the simulation reimplements just that glue, not the algorithm. A round: refresh matchups for the current phase → fill every open court → resolve a plausible random score for each live court → end each match (stats, rotation history, pooling) → `releaseStalePairings` → repeat until every player has reached `expectedGamesPerPlayer` or a safety cap (`maxRounds`, default 300) or a genuine deadlock (too few players left to fill a court) is hit.
  - **Random player counts.** `randomizePlayers: true` (config) ignores `playerCount` and calls `randomPlayerCount()` — an inclusive random integer in `[MIN_RANDOM_PLAYERS, MAX_RANDOM_PLAYERS]` (8–24, a realistic open-play turnout range) — picked fresh for that run. `cfg.playerCount` is overwritten with whatever was actually used so it's reported accurately everywhere downstream (report, UI, comparison table).
  - **CLI**: `node scripts/run-simulation.mjs` (`--players=`, `--courts=`, `--games=`, `--skillSplit=`, `--mentorshipMax=`, `--transitionMax=`, bare `--randomPlayers` flag — `--courts` also accepts a comma-separated list, e.g. `--courts=2,3,4`, to run the same session at each court count back-to-back and print a comparison table; when combined with `--randomPlayers` the headcount is resolved once and shared across all court counts so the comparison stays apples-to-apples) or import `runSimulation`/`printSimulationReport` directly.
  - **Developer page**: `src/components/DeveloperView.jsx`, reached via a "Developer? Run the rotation simulator →" link on the landing screen (same pattern as the existing "Organizer? Manage access codes" link) — a new `screen === "developer"` state in `PickleballOpenPlay.jsx`, no session/auth/Supabase involved. A small form (players, courts, games/player, beginner %, a randomize-players checkbox, a compare-2/3/4-courts checkbox) calls `runSimulation` directly in the browser on click and renders the result: summary line, phase counts, a Fairness Score badge, and a standings table reusing `StandingsView`'s table styles (`standingsTable`/`standingsHeadRow`/`standingsRow`/etc. — same look, no new table styling invented). Deliberately simple/read-only; no export, no persistence, nothing saved anywhere.
  - **Fairness statistics + score.** `calculateFairnessStats(playerSummaries)` reduces the roster's games-played counts to `{ minGames, maxGames, avgGames, stdDevGames, fairnessScore }` — population standard deviation (the roster *is* the whole population for the session, not a sample), rounded to 2 decimal places. `fairnessScore` condenses that into one 0-100 number for an at-a-glance read (100 = everyone played exactly the same number of games), built from the coefficient of variation (`stdDevGames / avgGames`, not raw stdDev) so it stays meaningful across very different `expectedGamesPerPlayer` settings — a stdDev of 1 game means something different at "3 games/player" than at "12 games/player," and the CV normalizes for that; clamped to `[0, 100]`, `100` when `avgGames` is 0. The multi-court comparison table (`--courts=2,3,4`, or the Developer page's compare checkbox) surfaces min/max/stdDev/score side by side so a widening spread at a given court count is easy to spot at a glance.
  - **`releaseStalePairings`: a simulation-only deadlock fix for Winner Pool Rotation's pairwise hold.** Real sessions always have enough waiting players to eventually fill both courts in a pair, but a *simulated* one can be configured with more courts than the player count can ever fill simultaneously — e.g. 16 players across 4 courts (paired 1&2, 3&4) can run at most 4 matches, but 12 players across 4 courts can only ever run 3, so one court in a pair permanently never gets a 4th match. Without this, the live app's ordinary pairwise-hold behavior (a finished court waits, `awaitingPair`, for its partner) would hold that court's players forever — they'd never be requeued, and would sit at whatever games count they had when the deadlock started rather than reaching `expectedGamesPerPlayer`. Called once per round after that round's matches end: any court still `awaitingPair` whose partner is (still) `"open"` — meaning this round's fill pass already had its one chance and the partner didn't get deployed a match — is force-released back to the queue immediately, rather than waiting indefinitely. This is orchestration the simulation adds for itself; it doesn't change `resolveWinnerPoolMatch`/`isPoolingRotation` or any pooling behavior the live app relies on.
- **PWA: installable, offline app shell, CONNECT.PH-branded.** `vite-plugin-pwa` (configured in `vite.config.js`) generates the Web App Manifest (`manifest.webmanifest` — name "CONNECT.PH Open Play Manager", short name "Open Play", `display: "standalone"`, theme/background colors matching `--color-primary`/`--color-bg`) and a Workbox service worker (`dist/sw.js`) at build time; both are auto-injected into `index.html` (`injectRegister: "auto"` adds the registration script, no changes needed in `src/main.jsx`). The service worker precaches the built app shell — JS/CSS bundles, `index.html`, icons, favicons — via `globPatterns`, and `navigateFallback: "/index.html"` serves that cached shell for any in-app navigation while offline (the app has no server-side routes, so the shell *is* the whole app once React takes over). Google Fonts (stylesheet + woff2 files) get a `CacheFirst` runtime-caching rule so custom fonts still render offline after a first successful load. Deliberately **no** runtime caching rule for Supabase requests — session/score data must always come from the network when available, never served stale; offline just means the shell still opens, not that live data works without a connection. iOS doesn't install from the Web App Manifest alone, so `index.html` also carries the Apple-specific meta tags (`apple-mobile-web-app-capable`, `apple-touch-icon`, etc.) needed for "Add to Home Screen" to launch standalone there. All icon/favicon assets (`public/icon-192.png`, `icon-512.png`, `apple-touch-icon.png`, `favicon-16x16.png`, `favicon-32x32.png`, `favicon.ico`, and `public/favicon.svg`) share one CONNECT.PH-inspired mark — a navy field, an open orange ring evoking the logo's "C", and a small orange connector dot at center — generated by `scripts/generate-pwa-icons.mjs`, a dependency-free script that hand-encodes both PNG (raw RGBA + `zlib.deflateSync` + a small CRC32 table) and ICO (a thin container wrapping the same PNG bytes) formats. Re-run it if the brand colors ever change (keep it in sync with `styles.js`'s `--color-primary`/`--color-secondary` and `favicon.svg`). No Vercel config changes needed — `dist/` (including `sw.js`, `manifest.webmanifest`, `registerSW.js`) is just more static output from `vite build`, which Vercel already serves as-is.

## Known limitations

- No real authentication (PIN-gated roles only, unenforced server-side)
- The Supabase anon key has full read/write access to session and access-code data (see `backend/README.md`)
- Player photos stored as base64 thumbnails in the same table as everything else
- Access codes and session data share the same trust boundary
- All three Progressive Skill Rotation phases (Mentorship, Transition, Competitive) now have real pairing logic — see Architecture above
- Adding a *fourth* rotation strategy is straightforward — the Strategy pattern (`RotationEngine` subclass + a case in `getRotationEngine`) and the mode picker both already support more being added
- Undo is one level deep and device-local for both "Undo regenerate" and "Undo last round" — neither is a full multi-step history/redo stack, and neither syncs to other devices; substituting or removing a player remains one-way with no undo
- Winner Pool Rotation's pairwise synchronization (holding a finished court until its pair partner also finishes) is resolved client-side on whichever device clicks "Confirm result" last; two scorers on different devices confirming both paired courts within the same ~1s Realtime sync window could theoretically race — not handled, same trust model as the rest of the app's optimistic concurrency
- No dedicated stats screen for partner/opponent frequency or court usage — that history is tracked per-player (`partnerCounts`, `opponentCounts`, `courtCounts`) but only Standings (games/wins/losses/streak) is surfaced in the UI today
- PWA offline support covers the app shell only (it can still *open* with no connection) — live session/score data is never cached and always requires the network, same trust model as the rest of the app
- PWA icons/favicons (`scripts/generate-pwa-icons.mjs`) are a simplified, hand-drawn CONNECT.PH-inspired mark (navy field, orange ring + dot), not a pixel-accurate render of the full logo file (the logo's wordmark and plug illustration can't survive down to a 16x16 favicon anyway) — swap in real exported assets from the logo source file if/when one's available
- No dedicated Apple splash-screen images (the `apple-touch-startup-image` matrix of per-device sizes) — iOS auto-generates a basic splash from the manifest's icon/background_color/name when none is provided, which was judged good enough against the effort of maintaining a full device-size matrix by hand

These are documented in more detail in [README.md](README.md) and [backend/README.md](backend/README.md).
